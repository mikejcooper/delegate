# Run trace: the lines

Part of RUN-TRACE.md: every field a trace line can have, and how to write each one. Read it when you write a line
by hand (`run_item.py line`, `start`, `end`) or need a field the fast path doesn't fill in; `run_item.py steps` fills
in a step's type, key, id and time by itself.

## Lines (one JSON object per line)
- **Header:** `{"header":true,"run":"<run-id>","label":"<short label>","request":"<request in a few words>","started":"<ISO time>"}`
- **Trigger matched:** `{"t":"<ISO>","entry_match":"<trigger id or null>","candidates":["<ids>"],"why":"<one line>"}`. A run that uses several triggers writes one such line per trigger, and its steps (forks included) add `"entry":"<trigger id>"`; steps without it belong to the first trigger.
- **Step:** `{"t":"<ISO>","id":"s1","from":"<parent step id>","step":"<short name>","trigger":"<what caused it>","result":"<outcome>","status":"done|skipped|uncertain|failed|needs_user","why":"<reason>"}`. In an item's run, `step` is the workflow step's title **word for word**, as the skill's "**Step N: <title>.**" heading gives it (e.g. `"step":"Screenshot the status report"`), never a paraphrase: `run_item.py` stamps the line with that step's key (`"wstep"`), and the board and the run reviewer place the line by that stamp, whatever its `type`. A name that is no step of the workflow is written unstamped with `"unmatched":true`; the output says so and lists the titles to use, so log it again under the right title. A line that is not a workflow step at all (a connection check, your context) adds `"wstep":null`. `failed` is a step that ran but didn't work, so its result can't be used: a tool errored, or a collector read nothing where there must be something (e.g. 0 services for every firm). `uncertain` is a result that might be right but couldn't be confirmed. Every step also gets `"type":"<label>"`, shown before the step name as `<label>: `. Use one of: `Email Read`, `Email Draft Created`, `Online Search/Check`, `Sorted`, `Skipped`, `Handed Off`, `Alert Assessed`, `File Changed`, `Page Check`, `Already Done`, `Approved Automatically` (a "Send it?" step answered yes by the Approve automatically switch), `Context Added` (the user's context for the run), `Fake Read` (a test used a canned answer or fake source), `Mocked` (a test refused a change and says what would have happened); a `Fake Read` or `Mocked` step also gets `"as":"<the type the real step would have had>"` (e.g. `"as":"Email Draft Created"`), so the board still sees which path the test took; if none fits, add a short one in the same style. Optional: `"title":"<up to 6 words>"` (the short name the board shows, e.g. "Give each alert an ID"; without it the board uses the matching workflow step's title, or `step`), `"because":"<why I did it, in plain words>"` (shown as **Why** on the dispatcher view; add it to every step), `"skill":"<name>"` for a hand-off to a skill, `"shot":"shots/<file>.jpg"`. A step that reaches an outside account through its connection adds `"via":{"connection":"<name>","method":"<connector|chrome|browser|api: the one actually used>","confirmed":"<how a write was checked, e.g. in Sent; false when it wasn't>"}`. A step that makes or sends something adds `"made":{"name":"<what it is, 2-4 words: News dashboard, Draft to Sam, Notion page>","kind":"<Web page|Picture|Email draft|Email sent|Page|Message>","href":"<where to open it>","preview":<a small picture or a few lines>}`: the outcome lists it by its `name` (never the step's title), with its kind and "from Step N: <step title>" underneath, a 96×64 `preview` on the left and an Open link. `href` is a `https://` link (the draft, the page, the message) or a file the board serves, `shots/<run-id>-<name>.<ext>`: copy a file the run made on this computer into the screenshots folder first, never a `file://` link. `preview` is a picture in the screenshots folder (`"shots/<run-id>-<n>.jpg"`: the image itself, or a screenshot of the page it made) or a few lines of text, `{"to":"<recipient>","title":"<subject or title>","line":"<its first line>"}`; never a full body. Leave out what doesn't exist. For the Builder's step list and step inspector, also optional and short: `"sub":"<the grey line under the title: only what the title doesn't already say>"` (e.g. title "Sign-in zero-days, last 24h", sub "None found · 3 searches", never "None found in the last 24 hours"); `"in":"<what went in, one plain sentence>"`; `"tags":["<2-6 short facts about what came out>"]`; `"warn":"<when the result doesn't match what was asked, one plain line>"`; `"io":{"in":{<the fields it was given>},"out":{<the fields it produced>},"flags":{"<out field>":"<why it looks wrong>"}}` (a few short fields each: IDs, names, counts, yes/no; never email bodies, passwords or tokens).
- **End:** `{"t":"<ISO>","end":true,"verdict":"<one sentence>","summary":"<one or two sentences>","flow":["<2-4 words>", "..."],"attention":"none|review|action"}`, plus `"deviations":[{"step":"<its title>","planned":"<what the path or connection says>","did":"<what was done instead>","why":"<why>"}]` for every change the run knowingly made from its path or a connection's method (none: leave it out), plus `"next":"<the one thing the user has to do>"` only when there is one (send the drafts, answer a question); most runs have none, so leave it out. `verdict` is the answer in at most 12 words (e.g. "Not linked to any new bug."). `flow` is 3–5 tiny steps the board shows under the outcome as `A → B → C`, the last one being the result (e.g. `["Read the alert","Searched for new bugs","Made test draft","No match"]`); without it the board falls back to the step types. A check that finished with no issue (e.g. an alert not linked to any bug) ends with `"attention":"none"`, even if you'd still mention something to the user: put that in `notes` (below), never in `next`. Use `review` or `action` only when a step found a real problem or is waiting on the user. A run with a `failed` step ends with `"attention":"action"`, and its `verdict` says what failed. Optional fields make the board's outcome box (a few plain lines, then what it created); write one only when it has something, never an empty or "none" entry: `"done":[{"k":"mail|next|file|inbox","t":"<what it is, a few words>","detail":"<one line>","href":"<link to it, when there is one>"}]`, only things that exist after the run (drafts, a hand-off, a saved file), each shown with a button to open it; one made by a step that logged `made` names that step's key in `"step"` (its `wstep`), so the two are one row, never two, e.g. `{"k":"mail","t":"2 drafts in Gmail, not sent","detail":"Bug note to you@example.com · CEO's article to name@example.com"}`; `"waiting":"<on whom and for what>"`, when the run stops for an answer or a choice; `"problems":[{"what":"<what went wrong>","why":"<the likely cause>","fix":"<a possible fix>"}]`, only for real errors; `"notes":["<a few words>"]`, anything that seemed off but didn't stop it, each a short bullet, not a sentence. Without `done`, the board works it out from the draft, hand-off and file steps.
  **The hand-off line says what was found.** Each item's `Handed Off` step (written by `run_item.py start`) carries `"found":"<one plain line>"` (its `--found`): what the trigger found for this item, in words a person would use: who sent it or where it came from, and what it is about ("Found a Savills email about a Stratford bid deadline"), never the trigger's name or the item key. The run page shows it as the first row of the steps, with "1 of N kept from M" from the trigger's read and keep steps, so those keep a number in their `result` ("Found 14 emails…", "2 … kept, 12 other").
  **How the outcome reads.** The board's Workflow outcome is a short timeline: a summary at the top, then only the steps that mattered (failed, waited on you, uncertain, made something, changed something outside, handed on), each from its step's `status` and `type`, the quiet ones as a count. So: give every step that makes something a type that says so (`Email Draft Created`, `File Changed`, `Design Drafted`, or one ending in `Created` / `Drafted`), every step that changes something outside one ending in `Sent`, `Posted`, `Reply` or `Updated` (`Slack Message Sent`, `X Reply Sent`; a test's `Mocked` step keeps it in `as`), and a step that couldn't confirm its result `uncertain`; otherwise it is drawn as quiet and the reader never sees it. Add `"summary":"<one or two plain sentences>"`: what the run did and what came of it, with the one or two facts that matter (e.g. `"Listed with **2 brokers**; both owners found on Companies House, one's base unconfirmed. The Slack message is held back."`), the first thing anyone reads; without it the board uses `verdict` and the first `facts`. Below the summary, Detail shows the rest as a short list, never paragraphs, so write it that way: `verdict` is the headline (the answer, not how you got it); then `"facts":[{"k":"<label, 1–2 words>","v":"<the value>","why":"<where it came from or why, a few words>"}]`, the 2–4 things this run worked out that someone checking it wants to see, each one line (e.g. `{"k":"Agency","v":"Estate Office Investments","why":"from the email footer"}`, `{"k":"Sent","v":"No","why":"you gave no answer when asked"}`). Don't repeat in `facts` what `waiting`, `problems` or `done` already say. In `verdict`, `facts` values and `notes`, wrap the one thing worth seeing at a glance in `**…**` (a name, an amount, a yes or no), at most once per line; no other formatting. For example: `"verdict":"Found the agency: **Estate Office Investments**. Not sent."`

## A workflow with a loop
A workflow with a `loop:` line (core-dispatcher, **A workflow with a loop**) is one run for all its items: its own trace
(`run_item.py batch`, header `"kind":"batch"`, ID `run-…`) holds the steps that run once and the run's end line; each
item that goes round the loop has its usual `<wf>-a<n>` trace, its header naming the run (`"batch"`) and the loop
(`"loop"`). Log each loop step on the item's trace and each once step on the run's, every one under its workflow step's
title, so the board can add the loop up ("2 Americas · 1 Europe") and show any one item in place. The run's `label` is
what it covers ("The 5 newest NY Times top stories"); its end line's `summary` covers every item, and names the ones that
stopped.

## How to write them
- **Plain words.** `step`, `result`, `verdict`, `summary` and `next` are one short sentence a six-year-old would follow (e.g. "Looked at my email", "Found 6 new emails, 2 from Google about my account"). Technical detail goes in `trigger` / `why`.
- **Say what it found, not how much it read.** A step's `result` (its Summary on the board) is what came out that matters for the next step, in a line: "A court case in Wiltshire", "About GTA 6's release; mentions a Manchester gamer once", never only a count or a size ("Read the article: 164 words"). Counts go in `tags` or `io`, beside the finding. The workflow's step says what to report; when it doesn't, report what the next step needs to know.
- **Summary on top, the detail underneath.** `result` and `tags` stay the short summary (the Summary tab). What the step read or made goes in `io.out` (the Data tab), so anyone can look one level down and see it, as short fields, not paragraphs:
  - **A read of a list** (a trigger's get, a feed, a search): `io.out.seen`, one line per item it saw, in the source's own words: `"<subject or headline> · <sender or source> · <time> · <its ID> · kept"` or `"… · stopped: <2-4 word reason>"` (e.g. `"Card payment declined · Revolut · 20 Nov 00:38 · AAMk… · stopped: bank notice"`). The keep step logs the same list, now with every kept or stopped mark.
  - **A read of one thing** (an email, an article, a page): the facts it found, one field each (e.g. `property`, `address`, `price`, `agent`, `dates`), and for the fact the next step relies on, the exact phrase it came from (`"quote":"Bid Deadline: Wednesday 2nd December 2026"`).
  - **A decision:** the answer and the phrase or fact it rests on.
  - **A write** (a note, a page, a message, a draft): what it wrote: the title, the recipient, the message text or the note's sections in a line each, and its link.
  - **Something it made that the user can open** (a page, a file, a report, a draft, a Notion page): also `"made": {"name": "<what it is, 2-4 words>", "kind": "<page|file|report|draft|note>", "href": "<where>"}` on the step line itself (beside `io`), so the outcome lists it with an **Open** button. `href` is a web link (`https://…`), a page the board serves (`pages/<file>`, as a workflow's own page script prints it), or the file's path on this computer (the button then copies the path). One per step; leave it out when nothing was made.

  A few lines per step (about 50-150 tokens); a long list of items, about 15 tokens each. Still no full bodies, passwords, tokens or personal ID numbers (**Privacy**).
- **Log after, never before.** Write a step only once it has finished, with its real outcome. Log decisions, not tool calls. Never rewrite earlier lines. End line goes last.
- **Hand-offs** to another skill are steps in the same trace (`skill` + `from`), not forks.
- **Privacy.** No passwords, tokens, personal ID numbers or full email bodies. Message and workflow IDs are fine.
- Logging must not change what a skill does.
- **Write them with `run_item.py`** (in the scripts folder, next to the rebuild command): `line <run ID> '<json>'` appends one line with the time and the next step ID filled in and rebuilds the board; `queue` lists every kept item on the Inbox at once (Queued) right after the trigger keeps them; `start` and `end` also write the item's header, its done-list lines and its recording. The request shows on the Inbox as a placeholder row from the moment its header exists, so it is never invisible while it looks for items. Hand-writing a line is only for what it can't express.
- **Real timestamps.** Never type or guess a time. Every `started` and `t` value comes from the clock: run `date -u +%Y-%m-%dT%H:%M:%SZ` in the same Bash call that writes the line (e.g. `T=$(date -u +%Y-%m-%dT%H:%M:%SZ)` then use `$T`). The board's "ago" is computed from these, so invented times make runs look hours old. Don't batch-write a whole trace at the end with one made-up time: write each step as it finishes, or take a fresh `date` per line.

## One item per workflow
When a trigger finds a list of items (e.g. emails):
- The first trace is the **request**: header gets `"kind":"trigger"`, its first step summarises what was found.
- The request header also gets `"skip_done":true|false` and `"auto_approve":true|false`: the **Run each item once** and **Approve automatically** switches as the dispatcher read them at the start.
- Each item the dispatcher runs gets its own trace in the **runs folder**, named after its workflow ID and attempt, `<wf>-a<n>.jsonl` (e.g. `wf-7c1e04ab-a1.jsonl`), with header `"run":"<wf>-a<n>"`, `"kind":"run"`, `"group":"<run-id>"`, `"wf":"<wf>"`, `"item":"<item key>"`, `"attempt":<n>`, a label naming the item, and `"rerun_of":"<wf>#<n>"` for a rerun. Its steps and end line go there; the trigger gets a step `forked → <wf>-a<n>`.
- Items the dispatcher links instead of running (already done) get one step in the request: `{"type":"Already Done","step":"seen → <wf>","label":"<item name>","link_wf":"<wf>","link_run":"<run that handled it>","result":"Already handled in an earlier run","status":"skipped",...}`. The board lists them under **Seen before**.
- Every new item runs: there is no pulling in without running. (Older traces have `"type":"Pulled In"` steps and `pulled` done-list lines; the Inbox still shows those items as Not run.) Changes made by hand ("skip wf-…", "mark wf-… done / needs you / not run", "delete wf-…", the Run each item once switch) write one step per item with `"hand":true` and the item in `"wf"`, never `link_wf`: `{"type":"Skipped","hand":true,"wf":"<wf>","label":"<item name>","step":"skipped → <wf>","result":"…","status":"done",...}` (types `Skipped`, `Marked Done`, `Marked Needs You`, `Marked Not Run`, `Deleted`, `Setting Changed`). The done list holds the change; `link_wf` would tell the board a trigger found the item again.
- Items that need no workflow get one `"status":"skipped"` step in the request (per item or group), saying why (e.g. "5 newsletters: no workflow").

## Runs without a trigger
"Run workflow …", "test workflow …" and "rerun workflow …" have no trigger: the request's trigger line has
`"entry_match":null` and `why` names the workflow and where its input came from (the latest item, a workflow ID,
the request, or its example). The item's run trace is written as usual. A test run's label starts with "Test:" and
its end line's `next` says it was a test and isn't counted as done.

## Screenshots
Every step done on a visible page gets a screenshot when it finishes, taken from its background tab by `tabId` (don't front it). Copy it to `<screenshots folder>/<run-id>-<n>.jpg` and add `shot` (`"shots/<run-id>-<n>.jpg"`: the board serves that folder as `shots/`). Prefer list views. Never capture sign-in pages, secrets or full email bodies; if a shot is skipped, say why in `why`.
